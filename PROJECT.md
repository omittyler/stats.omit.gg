# stats.omit.gg — Project Documentation

## 1. Project Summary

A Call of Duty Challengers (amateur/semi-pro tier) player and team statistics hub, modeled conceptually on [breakingpoint.gg](https://breakingpoint.gg) (which covers the pro-level CDL). Lives as a standalone app on the subdomain `stats.omit.gg`, linked from the main omit.gg Webflow site (not embedded as an iframe).

**Explicitly excluded**, per breakingpoint.gg being a reference, not a template to clone: their proprietary "BP Rtg" custom rating stat, and their "Cards" collectible feature. Everything else structurally is fair game to adapt.

The point of building now is to have a working system live and ready *before* the 2027 season starts, using the 2026 season as the dataset to build and test against.

## 3. Architecture Decisions (already made — do not re-litigate without reason)

| Decision | Choice | Why |
|---|---|---|
| Data layer | Supabase (Postgres) | Free tier covers early scale, relational fit for granular per-map/per-weapon/per-round stats, pairs easily with Next.js |
| Frontend | Next.js on Vercel | Cost, SSR/SEO for player/team pages, ecosystem fit with Supabase |
| Hosting | Standalone app on subdomain `stats.omit.gg`, linked (not iframed) from main omit.gg Webflow site | Subdomain is indexable by search engines; an iframe would not be |
| CMS | Not using Webflow CMS for stats data | Webflow CMS item limits and filtering engine don't scale to granular per-map/per-weapon stats; user wants full data ownership |
| Data ingestion (stats) | Provider supplies stats data via Google Sheet/CSV/Excel, imported through a password-protected admin page | Not manual entry. Admin tool parses CSV/XLSX, matches rows against existing players/maps/events (update, not duplicate), shows a pre-commit preview (e.g. "14 new stat lines, 3 updates, 2 flagged rows") before writing to the DB |
| Data ingestion (rosters/logos/placings) | Manual one-time pull from the Call of Duty Esports Wiki into CSV + image files, dropped into the repo — see §6 | Wiki domains are blocked to Claude's browser tooling in this environment and returned errors on direct fetch (fandom.com: policy block + HTTP 402; liquipedia.net: HTTP 403, consistent with their anti-scraping stance). No live API integration was attempted or should be attempted against either site without going through their official, ToS-compliant APIs |
| Future nice-to-have | Direct Google Sheets API sync to skip manual export | Not in v1 scope |
| Data granularity | **Superseded 2026-08-30.** Only per-player, per-event aggregate stats exist (an Overall combined-modes line, plus separate Hardpoint/Search & Destroy/Overload breakdowns) — no per-map, per-round, or per-weapon data | Confirmed 2026-08-30: this is the real extent of what the stats provider supplies for BO7, not an interim/partial drop. Overturns the earlier "must be per-map/per-round" requirement — that granularity isn't available and isn't coming |
| Game modes (Challengers) | Black Ops 7 plays 3 modes: Hardpoint, Search & Destroy, Overload — no Control | Confirmed 2026-08-30. "Overall" in the stats exports is a combined/all-modes rollup, not a 4th mode |
| Game title tracking | `events` (and stats tables derived from it) need a `game` field (e.g. `Black Ops 7`, `Modern Warfare 4`) alongside `season` | Confirmed 2026-08-30: the 2026 season (all `placings.csv` data so far) is Black Ops 7; the next season will be Modern Warfare 4 (`data/incoming/mw4_stats/` created in advance, currently empty) — a season can't be assumed to map 1:1 to one game title going forward |
| Admin auth | Simple shared-password gate on the admin import page (v1) | Fastest to build; only the user and their stats provider need access. Revisit if admin access needs to scale to more people later |
| Standings scope | Both per-event standings AND an aggregated overall-season standings view (points summed across events) — not per-event only | The 2026 season (the initial dataset) has no cross-event running system yet; the whole point of this project is to have that aggregated view ready before the 2027 season starts |
| Points formula | **Superseded 2026-08-26.** CDC Points are NOT manually supplied — they're computed from a placement (rank) looked up against an official points scale that varies by event type (Cup / Elite / Major-Open / Finals-Champs). Full scale in `data/reference/cdc_points_and_prizing.md`. Finals/Champs awards **zero CDC points** (confirmed), prize money only | User provided the official CDC Points & Prizing tables; this is a real formula now, not an unknown |
| Prize money | Track prize earnings per placement and surface aggregated season earnings on Team pages and Player pages | User wants earnings displayed as part of team/player season history, not just internal bookkeeping |
| Team logo fallback | A sentinel `Default` team / `Default.png` logo exists in the teams lookup. When importing player statistics or bracket/match data, if a team name doesn't match any known team, use `Default.png` as its logo but keep the real team name from the import — never drop/rename the team | Stats and bracket imports will reference teams by name; not every team will have a logo on file at import time, and the site shouldn't break or hide a team just because artwork is missing |
| Player photo fallback | `public/players/DefaultPlayer.png` is the fallback photo for any player without a photo on file (confirmed 2026-08-26) — same pattern as the team logo fallback, applied at the player level | Not every player will have a photo sourced/available; the site shouldn't break or hide a player over missing artwork |
| Generic/placeholder team name disambiguation | Confirmed 2026-08-26: any generic placeholder team label (e.g. "Orgless" — meaning "no org/sponsor," not a real brand) must be suffixed per-occurrence, e.g. `Orgless (EU S4)`, `Orgless (EU S2)` — never written verbatim as just `Orgless` | These labels get reused across unrelated squads that each happen to lack a sponsor name (confirmed case: "Orgless" in EU Stage 2 was one roster, EU Stage 4 was a totally different one). Writing them verbatim would silently merge unrelated teams' points/placements together in aggregated standings |
| Parent-org sibling squads | Confirmed 2026-08-26: "Stallions," "Stallions Black," and "FC Stallions" are one parent organization fielding multiple separate competing teams — NOT the same team to be merged. Same pattern already seen with Falcons Academy Green/White/Black. Keep sibling squads as distinct `team_name` values even when they clearly share a parent org | Standings/points are tracked per competing team, not per parent org; merging siblings together would misattribute one squad's results to another |
| Player transfers are normal, don't imply a team rename | Confirmed 2026-08-26: players moving between different-named teams across events (or even the same team's roster fully turning over) is normal and does NOT mean the two team names are the same org/should be merged. Default to keeping team names exactly as given per event, even when roster overlap between two differently-named teams is high (e.g. Champs' "OMNiA Invicta" sharing all 4 players with Major 3/4's "Exceptional Gaming"; Champs' "Treaty1Gaming" sharing all 4 with "ASK Esport"; Champs' "Decimate Gaming" sharing 3 of 4 with Major 3's "KAOS Esports") | Only merge/normalize team names on an explicit same-org confirmation from the user (as with Carolina Piranha, CGMT, Atrocity) — roster similarity alone, however strong, isn't sufficient signal on its own |

### 4.1 Match Page — `/matches/[series]`
**Un-cut and built, 2026-09-02.** Originally cut from v1 scope 2026-08-30 for lack of match-level data - real match/map data arrived later (§8ag) and this page shipped the same day (§8ah). Every item below was actually delivered, at the real URL `/matches/[series]` (not `/match/[id]` as originally speculated - `series` is the source data's own Series ID, e.g. `SR001`, used directly as the slug):

- Header: event name, both teams (logo + name), overall series score (e.g. 3-2), LAN/Online badge. (No date/time - not in the source data, not shown rather than guessed.)
- Map-by-map summary strip: map name, mode, per-map score, color-coded by which team won, plus a map thumbnail image. **Thumbnails wired in 2026-09-02** — `data/incoming/bo7_maps/*.webp` moved to `public/maps/` and matched by lowercased map name (`lib/matches.ts` `getMapThumbnail`); the 2 map names seen in seeded data but outside the official pool (Blackheart, Plaza — not in `data/reference/match_format_rules.md`) fall back to a blank placeholder tile rather than a fabricated image. The chip row is a single horizontal-scrolling row so a Bo7 (7 chips) never wraps.
- Tabbed stat table (`components/MatchTabs.tsx`): **Overview** tab (series aggregate, k/d/a/damage summed across every map a player played) + one tab per map actually played, generated dynamically from however many maps exist for that match (never a fixed Bo3/5/7 count).
- Columns per player: Kills, Deaths, K/D, +/-, Damage on Overview; per-map tabs additionally show that mode's specific fields (Hardpoint: Hill Time/Obj K/Contest; Search and Destroy: Plants/Defuses/First Bloods/First Deaths; Overload: Goals). No proprietary rating column (the breakingpoint.gg reference layout has one; we have no data for it and didn't fake one).
- Not delivered / not attempted: kill%/damage% bar graphs (never actually asked for once the real spec conversation happened) and map veto info (not in the source data).

### 4.4 Standings Page — `/standings`
**Superseded 2026-08-30 — points are earned by, and travel with, the PLAYER, not the team.** A team's own placements don't accumulate into a persistent team total; a team's standing is the sum of its *current* roster's individual point totals, recomputed from each player's full history whenever the roster changes. See §8d for the full model, why this needed real event dates, and the new `/players` page (individual leaderboard) this necessitated. Everything below this note describes the *event_type*/points-scale mechanics, which are still accurate — only the "whose total is it" question changed.
- Tabs must be **dynamically generated** from an `events` table (`type`: Cup / Elite / Major / Champs, plus `season`/`stage`/`region`/`order` for sequencing — see §5). Do NOT hardcode tabs like CDL's "Major 1–4/Champs" — Challengers has more event types and new ones shouldn't require code changes.
- Columns: Rank, Team, Points, MW (Match Wins), ML (Match Losses), MW%, GW (Game/Map Wins), GL (Game/Map Losses), GW%.
- MW/ML/GW/GL/win% are derived/computed from match and map results already in the database.
- **Superseded 2026-08-26 — Points ARE computed**, not manually supplied. A team's `points` for an event = lookup(event_type, placement) against the official CDC Points scale in `data/reference/cdc_points_and_prizing.md`. Summary of the scale:
  - **Cup:** 1st=2000 ... down to 33rd-64th=100. (Data entry is capped at top 32 regardless — see scope decision below.)
  - **Elite:** single combined 1st-12th scale (15000 down to 2500), but see the two-stage nuance below — a team's placement number for lookup purposes can come from either the Qualifier or the Playoff stage.
  - **Major/Open:** 1st=25000 ... down to 49th-64th=500.
  - **Finals/Champs:** **zero CDC points, confirmed** — cash prize only, since qualification into Finals is already earned via points from other events during the season.
  - Exact placement-range → points/prize values are in the reference file; don't duplicate/hand-copy them here, link to it.
  - **Elite mechanic (confirmed 2026-08-26):** Elite runs as multiple independent stages per season (Stage 1, Stage 2, etc.), each a 12-team Qualifier feeding a Playoff, each stage scored off the same 1st-12th scale. Top 8 from the Qualifier advance to Playoff and get their points/prize from Playoff placement (1st-8th); the bottom 4 (9th-12th) are eliminated at the Qualifier and get their points/prize from Qualifier placement directly (9th-10th/11th-12th tiers). **Confirmed: the placement data itself will already be a single, final, pre-resolved number per team per stage** (e.g. we're told directly "Team X placed 9th in Stage 1", not two separate Qualifier/Playoff numbers to reconcile ourselves) — so `event_placements` needs one row per team per Elite *stage*, not separately per Qualifier/Playoff. Qualifier and Playoff still matter as separate brackets for match/bracket display once stats data exists, but placement/points attach at the stage level.
  - **Region structure (confirmed 2026-08-26):** Elite has region-based standings (NA/EU/etc.), used to seed future Elite stages within that region. Separately, there is ONE global ranking (combining all regions) used to seed Majors/Opens. This means the standings page needs both a per-region view AND a combined global view — not just per-event-type tabs. `events` needs a `region` field (populated for region-specific events like Elite and likely Cups; null/global for Majors/Opens/Finals which aren't region-split).
  - **Scope decision (2026-08-26): only placements 1st-12th are tracked for Elite events.** The Elite Qualifier bracket can be much larger (e.g. 32 teams), but everyone below 12th earns zero CDC points per the scale — so `placings.csv` only needs rows for the top 12 per Elite stage, not the full qualifier field. This also sidesteps needing rosters/logos for the large tail of ad-hoc teams that don't place.
  - **Scope decision (2026-08-26): Cup events are capped at top 32, even though the official scale pays out to 33rd-64th.** User decided to skip 33rd place onward for Cups regardless of what the source shows — this is a deliberate scope cut, not a reflection of the official points scale. Cup 1 NA (32 rows) already reflects this cap. Major/Open is the only event type recorded in full range (seen as far as 83rd place) — see `data/incoming/README.md` for the per-type rule.
- **Decided (2026-08-26):** v1 includes BOTH per-event standings tabs AND an aggregated overall-season standings view (points summed across all events for a season). This is a core requirement, not a nice-to-have — see timeline context in §2. The `event_placements`/points schema and queries need to support summing across events within a season, not just per-event lookups.
- **Refined (2026-08-26):** "aggregated season standings" isn't a single flat view — there's a **per-region** aggregate (drives future Elite seeding within that region) and **one global** aggregate combining all regions (drives Majors/Opens seeding). The standings page needs a region dimension alongside event-type tabs, not just one combined table.
- **Buildable now**: Rank/Team/Points — Points can now be computed from placement once `placings.csv` lands (§6), rather than needing a manually-supplied points value. MW/ML/GW/GL/win% columns are **blocked** on match data.

## 5. Draft Database Schema (tentative — pending real stats data sample)

Do not treat as final. Adjust field names/structure/granularity once the real stats data sample arrives. `players`, `teams`, `events`, and a placings/points table can be populated with real data now (§6); the rest stay schema-only until stats data arrives.

- **`players`** — bio fields, team reference, socials, photo. Photo resolution falls back to `public/players/DefaultPlayer.png` when a player has no photo on file — see §3 "Player photo fallback"
- **`teams`** — name, logo, org, coach, socials. Logo resolution must fall back to a `Default.png`-style logo (keeping the real team name) when a team encountered during stats/bracket import has no known logo — see §3 "Team logo fallback" and §6
- **`events`** — name, type (Cup/Elite/Major/Champs), season, `stage` (for Elite: Stage 1, Stage 2, ...), `region` (nullable — set for region-specific events like Elite/Cups, null for global events like Majors/Champs), order/date. Elite's placement/points attach at the stage level (one final placement per team per stage — see §4.4), even though Qualifier+Playoff are separate brackets internally for match display purposes once stats data exists
- ~~`matches`, `maps`, `player_map_stats`, `player_weapon_stats`~~ — **Cut 2026-08-30**: confirmed the available stats data has no match/map/weapon-level granularity (§2, §3) and none is expected. These tables are removed from the schema, not just deferred.
- **`player_event_stats`** (new, 2026-08-30) — one row per player per event, matching the shape of `data/incoming/bo7_stats/*.csv`: player, team (as fielded for that event — same per-event-roster philosophy as `event_placements`, §3), event reference, `matches_total/w/l`, `maps_total/w/l`, then one column group per stat block — **Overall** (combined across all modes played that event) plus **Hardpoint**, **Search & Destroy**, **Overload** (the 3 real BO7 modes — no Control, see §3), each with kills/deaths/K-D/assists/+-/damage/etc. for that mode. **Full column-by-column mapping (2026-08-30) in `data/reference/player_event_stats_columns.md`** — 104 columns total (7 identity/summary + 16 Overall + 26 Hardpoint + 28 Search & Destroy + 25 Overload + `event_id`/`game`). A handful of source abbreviations (`N/T`, `R K/D`, `SR`, `DR`, `HT`, `ObjK`, `CON`, `E/10`, `WR%`, `GLS`, `OCK`) have unconfirmed exact meanings — columns are named literally after the abbreviation for now, not blocking, see the reference file. Powers Player page headline stats + Event Stats section (§4.3), and — via rollup across a team's roster for an event — Team page's Team Stats section (§4.2).
- **`event_placements`** (renamed from `standings_points`, 2026-08-26) — team, event, placement (rank or tied-rank value, e.g. 5 for a "5th-6th" tie), **plus the 4 roster players for that specific placement** (added 2026-08-26 via `player1`-`player4` in `placings.csv` — see §7). **`points` and `prize_usd` are NOT stored directly** — computed at query time (or via a materialized/derived column) by looking up `(event.type, placement)` against `points_scale`. Populated from wiki placings data now (§6). The per-placement roster is what makes the 25%-per-player prize split (§3) computable immediately, without waiting on full player statistics.
- **`points_scale`** (new, 2026-08-26) — reference table encoding `data/reference/cdc_points_and_prizing.md`: `event_type`, `placement_min`, `placement_max`, `cdc_points`, `prize_usd` (and a regional variant for Cup — NA/EU vs AP/LA prize amounts differ even though CDC points don't; model as either a `region` column or two prize columns, decide when building). This table is the actual "points formula" — see §3.
- **Prize money aggregation** (new, 2026-08-26): team-level season earnings = sum of `prize_usd` across that team's `event_placements` for the season. Player-level earnings = team's prize for that event split evenly 4 ways (25% each) across the 4 players on the roster **at the time of that event** — confirmed 2026-08-26. This means player earnings depend on knowing the active roster per event, not just the team's current roster — if the 2026 season roster was static all year this is trivial, but flag it if any team changed lineups mid-season (see §7).

## 6. Data Intake Process (rosters, logos, placings)

Source: [Call of Duty Esports Wiki](https://cod-esports.fandom.com/wiki/Call_of_Duty_Challengers), 2026 season pages. This is a manual, one-time pull done by the user — not an automated scrape or API integration (see §3 for why: both the fandom wiki and Liquipedia are inaccessible to Claude's tooling in this environment, and Liquipedia's block in particular reflects a deliberate anti-scraping/ToS posture that should be respected, not routed around).

**Process:**
1. User copies team/roster/placement tables from the wiki into a spreadsheet, and separately downloads player photos and team logos. **In practice for `placings.csv` (2026-08-26):** user instead pastes the raw wiki table text (placement table + roster listings) directly into chat, one event at a time, and Claude transcribes it into the CSV — this works well and is the expected pattern going forward for remaining events. When source data has a genuine ambiguity (e.g. a name mismatch between the placement table and roster listing), Claude flags it and asks rather than guessing.
2. Spreadsheet/transcribed data exported as CSV and dropped into `data/incoming/` in this repo. Expected files and columns are documented in `data/incoming/README.md`: `teams.csv`, `players.csv`, `placings.csv`. Note `placings.csv` should record each team's raw placement (rank) per event — NOT a points value; points are now computed via `points_scale` (see §5).
3. Images dropped into `public/players/` and `public/teams/` respectively (see README.md in each folder for naming convention).
4. Once files are present, build a one-off seed script to load them into Supabase — this does not need the full admin-import-tool UI (that tool is specifically for the recurring stats-provider workflow, see §3).

**Status as of 2026-08-26:** `teams.csv` dropped in — a simple `Team Name` / `File Name` (logo) lookup table, 26 rows. All 26 corresponding logo PNGs (including `Default.png`) are already present in `public/teams/` and verified to match the CSV filenames exactly. Includes a special `Default` / `Default.png` sentinel row: when player-statistics or bracket/match imports (future, from the official stats provider) reference a team name not present in this lookup, that team should get `Default.png` as its logo while keeping its real name from the import — never dropped or silently renamed. This fallback logic needs to be built into whatever import/matching code resolves team logos, not just this one-off seed script. `players.csv` and `placings.csv` (and player photos in `public/players/`) not yet dropped in.

Notable implementation decisions:
- `points_scale` uses `prize_usd` (NA/EU or the only prize) plus a nullable `prize_usd_ap_la` (Cup only, since AP/LA Cup prize differs from NA/EU even though CDC points don't) — resolves the "model as region column or two prize columns" open item from §5.
- `event_placements`/`player_event_stats` team resolution: any `placings.csv` team not already in `teams.csv` gets auto-created with the `Default.png` fallback logo at seed time (implements the §3 fallback rule in code for the first time, not just as a stated rule).
- `player_event_stats`' team-code problem (bo7_stats files use codes like `TBG`/`P7N`/`HUN`, not full names) is resolved by looking up each stat row's player name directly in `placings.csv` for that event, case-insensitively (the two sources capitalize handles inconsistently), storing `placings.csv`'s spelling as canonical.
- **Fuzzy (prefix) matching requires corroboration, added after a real mistake was caught 2026-08-30.** When exact matching misses (bo7_stats truncates/shortens names in both directions, e.g. "D3" vs "D3L1V3R"), a unique prefix match is only trusted if at least one *other* player under the same bo7_stats team code already exact-matched to that team. Caught via a Postgres duplicate-key collision against the already-correct "tK" row, cross-checked, and fixed by requiring corroboration in code rather than trusting manual review alone. 36 of the original 39 held up under the stricter check and are recorded in `scripts/seed/confirmed-aliases.json` (committed, not gitignored — an auditable record of what's been verified, not a regenerated report).

## 8d. Points Are Per-Player, Not Per-Team (added 2026-08-30)

**Major correction, caught by the user after seeing the first Standings page's numbers looked wrong.** CDC points are earned by, and travel with, the *individual player* — not the team. If a player leaves OMiT for Project 7, the points they personally earned go with them; OMiT doesn't keep them and Project 7 doesn't start them at zero. The original team-level aggregation (first cut of `/standings`) was architecturally wrong, not just buggy.

**Resolved model:**
- When a team earns points for a placement, **all 4 roster players individually receive the full amount** (not split — confirmed 2026-08-30, this is different from how prize money is split, §3).
- A team's *current* standing = sum of its *current* roster's individual point totals. This means a team's ranking can change from a roster move alone, with zero new results.
- "Current roster" = whichever team each player's **most recent event by real date** shows them on. This needed actual calendar dates, which nothing in the schema had before — `events` didn't distinguish "Cup 5" from "Elite Stage 2" chronologically, only by type-specific ordinal numbers that don't interleave predictably (is Cup 5 before or after Elite Stage 1? no way to tell without a real date).
- **User provided the real 2026 season schedule** (Cups 1-13, Elite Stages 1-4, Majors 1-4, Champs — see `scripts/seed/lib/eventDates.js` for the full table). Confirmed: the same date applies across all 4 regions for Cup/Elite (no per-region date variation to model). One event on the schedule, **"LCQ" (2026-07-05, Last Chance Qualifier)**, was confirmed to need no placement data — disregarded, not a gap.
- Added `events.event_date` (migration: `supabase/migrations/2026-08-30-add-event-date.sql`, since `schema.sql`'s `create table if not exists` doesn't retroactively add columns to the already-live table). Seed script populates it via the new date lookup.
- New shared computation in `lib/standings.ts`: builds player totals first (every event a name appears in, full points each, tracking most-recent date/team), then rolls those up into team totals by current-team grouping. Powers both `/standings` (team view) and the new `/players` page (individual leaderboard, which didn't exist before this correction).

## 8f. Real Duplicate Rows From a NULL-Uniqueness Bug (added 2026-08-30)

User noticed `/standings`/`/players` totals looked additive across re-seeds and checked the actual `event_placements` row count: **3,123 instead of the expected 1,692.** Root cause, confirmed via SQL: `events.unique(name, region)` never caught duplicates for Major/Champs events, because their `region` was `NULL` — and `NULL` is never equal to `NULL` in SQL, so the constraint silently did nothing for them. Every `npm run seed` re-run created a **brand-new** "Dallas Open"/"Birmingham Open"/etc. event row instead of matching the existing one (confirmed: exactly the 5 null-region events — the 4 Majors + Champs — each had 10 duplicate rows; Cup/Elite events, which always have a real region value, were never affected).

**Fix (migration: `supabase/migrations/2026-08-30-dedupe-events.sql`):** repoint every `event_placements` row from a duplicate event onto one canonical row, delete the now-orphaned duplicates, de-duplicate any `event_placements` rows that collapsed onto the same `(team_id, event_id)` as a result, then normalize `region` to `''` instead of `null` for global events (and set `NOT NULL` going forward) — `''` behaves correctly under the existing constraint, `NULL` never did. `seed-events-and-placements.js` and `schema.sql` updated to never write `null` for region again.

**Lesson for this schema going forward:** a plain SQL `unique` constraint across a nullable column silently fails to dedupe null rows. Either avoid `NULL` in any column that's part of a uniqueness check (the fix taken here), or use a `coalesce()`-based unique index if `NULL` needs to stay meaningfully distinct from other values elsewhere.

**Verified fixed 2026-08-30:** the migration needed two follow-up corrections mid-run (dedupe-before-repoint ordering to avoid a constraint violation on `event_placements`, then the same treatment for `player_event_stats`, which also references `events(id)` and was missed initially). After all three passes: `event_placements` = 1692 (correct), `player_event_stats` = 759 (correct), and both counts now stay stable across repeated `npm run seed` runs. `/standings` and `/players` confirmed showing correct numbers.

This is the same class of gap the §8w/§8x/§8y notes already describe from the other direction (a team's own history missing an off-season signee) - this is the mirror case, a team's history having since moved past a player who's still clinging to a stale attribution.

- **`computeStandings()`** now also builds `teamLatestEventDate` (team name → its own latest real event date, independent of any player) and stamps each `PlayerStanding` with a new `rosterStale: boolean` - true when that player's `currentTeam` attribution's date is earlier than that team's own latest event date. Stale players are excluded from `teamTotals` entirely (no points/roster contribution to that team), but keep their own real point total and `currentTeam` (shown as their last known team - still the best information on record, just not "current" from the team's side) on their own player page.
- **`app/teams/[name]/page.tsx`**'s `currentRoster` filter now also requires `!ps.rosterStale` - Wrecks/Standy fall out of Current Roster and, since they're still in this team's own placement history, land in Previous Players automatically (no other change needed there).
- This is a general fix, not an OMiT-Brooklyn-specific patch - it corrects every team with the same latent pattern, not just this one. Pure runtime logic in `lib/standings.ts`/`app/teams/[name]/page.tsx` - no data change, no reseed needed, just a dev server restart/hard refresh.
- Not yet verified live - user should check OMiT Brooklyn (Wrecks/Standy → Previous Players) and spot-check a couple of other teams with mid-season roster turnover.

## 8ag. Match/Map-Level Data - Schema and Seed Script (added 2026-09-02)

User provided genuine match-and-map-level data - `data/incoming/bo7_match_stats/BO7 Season - {HP,Overload,Search and Destroy} Match Map Data.csv`, one file per mode, ~32k rows total, per-player-per-map for the whole season. This is what the Match page (§4.1) was cut from v1 for lack of - now buildable. Schema and seed script landed this session; the actual Match page UI is next (not built yet).

**Source data shape** (confirmed with the user column-by-column, not guessed): each file has a single header row (not bo7_stats' usual double-header), columns 1-20/19/21 (mode-dependent) give one player's stats for one map - `Player, Team (code), Vs, Series, [mode] match ID, Map, Map #, Result, points/rounds for/against, K, D, A, Non-Traded, Headshots, Damage`, plus mode-specific fields (Hardpoint: Hill Time/Objective Kills/Contest/Time; Search and Destroy: Plants/Defuses/First Bloods/First Deaths/Rounds; Overload: Goals/Objective Kills/Time). Everything past that - a repeated duplicate of the match-metadata columns, then an ambiguous per-named-block section that never cleanly reconciled with the main stats - is explicitly out of scope; the user gave the exact cutoff column per file (HP: AG/33, Search and Destroy: AH/34, Overload: AF/32) and confirmed we don't need anything past it.

**No event/tournament column at all** - just a `Series` ID (e.g. "SR001") spanning the whole season across every event. The user provided the exact Series-number-range → event mapping (`scripts/seed/lib/matchSeriesRanges.js`); ranges not covered by any listed range (SR412-436, SR614-701) are gaps, skipped entirely rather than guessed. Region is a separate wrinkle baked into the ranges module: Cup events keep one name across all 4 regions (a separate region column, §8f), Elite events embed the region in the name itself - either way, the seed script tries every plausible `{name, region}` candidate for a series and picks whichever one actually resolves the most of that series' real players against `placings.csv`'s roster for that event (reusing the existing `resolvePlayerTeam`/`buildPlayerTeamIndex` machinery - team CODEs like "P7N" in this data are never decoded directly, since resolving by PLAYER NAME instead gives back the real team name for free, same mechanism already proven for `player_event_stats`).

**New tables** (`supabase/migrations/2026-09-02-add-match-map-data.sql`, also appended to `schema.sql`): `matches` (one row per Series - event_id, team1_name, team2_name), `match_maps` (one row per map/game within a match - mode, map_name, map_number, team1_score/team2_score), `match_map_player_stats` (one row per player per map - k/d/a/non_traded_kills/headshots/damage plus nullable mode-specific fields, never 0 for a field that doesn't apply to that map's mode).

**New seed script** (`scripts/seed/seed-match-maps.js`, wired into `index.js` after `seedEventsAndPlacements` since it needs event IDs to already exist): parses all 3 files into per-map "games" grouped by `(Series, Map #)` - NOT by the mode-specific match-id column (e.g. "HP001"), despite that looking like the obvious key. First real run (2026-09-02) surfaced that column is only populated for the first ~200 of the HP file's 12640 rows and blank for the rest, silently collapsing nearly the whole file into a handful of buckets (61 games total instead of thousands) - caught via temporary `[debug]` counters added to the script, confirmed against the raw file with `awk`, then fixed by switching to `(Series, Map #)`, which is always present and unique per game within one series. Groups games by Series, resolves each series to an event/region and every player to a canonical name + real team, then upserts all three tables. Writes three gitignored reports on anything it couldn't confidently resolve, matching the existing `unresolved-*.json` convention: `unresolved-match-series.json` (couldn't pick an event/region), `unresolved-match-players.json` (an individual player name didn't match any roster - these rows are still seeded for whoever DID resolve on that map, just skipped individually), `scoreless-match-maps.json` (a map where one team's score couldn't be determined because nobody from that team resolved - now also correctly triggered when a resolved team's own score cell is blank, not just when nobody from that team resolved at all).

Two more real-run bugs fixed the same day: (1) a null-vs-undefined gap in the scoreless-map check - `toNumber()` can return `null` for a blank score cell, which isn't `undefined`, so a malformed row was slipping through and hitting `match_maps`' not-null constraint; now only a non-null score locks in per team, so a teammate's still-good row can fill in if the first one seen was blank. (2) Supabase/PostgREST caps a plain `.select()` at 1000 rows by default - the re-fetch used to build `matches`/`match_maps` id lookups after upserting (610 and 2300+ rows respectively) was silently truncated, sending `null` match_map_id into `match_map_player_stats` for anything past row 1000. Fixed with a paginating `fetchAllRows()` helper (`.range()` in a loop until a page comes back short).

**First real run (2026-09-02)**, after the three bugs above were fixed: 610 matches + 42 unresolved series + 113 gap series = 765, matching the full series count exactly - a good internal consistency check. 16,841 player-stat rows landed with no crash. `unresolved-match-series.json`'s 42 entries are almost entirely lower-bracket entrants at the Majors (Dallas/Birmingham/Paris) that `placings.csv` never recorded at all (some literally named "Chall 113"/"Challenger 112"/"YOL 19" etc. - anonymous placeholder entrant IDs, same already-accepted gap pattern as `unresolved-player-event-stats.json` elsewhere in this project) - not fixable, not fixed.

Restricting the alias fallback to only the final resolution pass barely moved the number (529 -> 528) - the REAL cause was one level deeper: a confirmed alias is a real fact about that player, but not proof they played in THIS specific series. Accepting one whose `team_name` didn't match either side already established by strict resolution introduced a false 3rd team, failing the exactly-2-teams check for series that would have passed cleanly if that one player had simply stayed unresolved. Fixed by keeping every distinct `team_name` ever confirmed for a name (`teamNames`) instead of collapsing to one; when a series already has 2 known teams, checks for an exact match against one of them (a fact, not a guess) and only falls back to the single most-common team (`bestTeamName`) as a last resort when there isn't enough context yet. That held the 610/42 baseline and pushed player-stat rows to 18116, cutting unresolved individual players to 202.
